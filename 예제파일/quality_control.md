# Part A. Guardrail: 개인정보보호 체크 (PII Guardrail)

> **목적**: AI 응답에 고객의 개인정보가 포함되지 않도록 자동 검출합니다.
> 판정 트랙의 첫 번째 관문으로, 개인정보가 검출되면 Fail 판정의 근거가 됩니다.

---

## 1. 개인정보 검출 대상

| # | 정보 유형 | 패턴 예시 | 위험도 |
|---|----------|----------|--------|
| 1 | 주민등록번호 | 6자리-7자리 (예: 900101-1234567) | 🔴 Critical |
| 2 | 신용카드번호 | 4자리-4자리-4자리-4자리 | 🔴 Critical |
| 3 | 계좌번호 | 은행명 + 숫자 10~14자리 | 🔴 Critical |
| 4 | 여권번호 | 영문 1~2자리 + 숫자 7~8자리 | 🔴 Critical |
| 5 | 전화번호 | 010-XXXX-XXXX, 02-XXX-XXXX | 🟡 High |
| 6 | 이메일 주소 | xxx@xxx.xxx | 🟡 High |
| 7 | 운전면허번호 | 지역코드 + 숫자 조합 | 🟡 High |

---

## 2. Guardrail 프롬프트 (PII 검출용)

AI 응답을 생성한 후, 아래 프롬프트로 **별도의 LLM 호출**을 하여 개인정보를 검출합니다.

```
# Role
당신은 개인정보보호 전문 검수관입니다.
AI가 생성한 고객 응답 텍스트에서 개인정보(PII)가 포함되어 있는지 검사합니다.

# 검사 대상 텍스트
{ai_response}

# 검사 항목
아래 개인정보가 텍스트에 포함되어 있는지 확인하세요:
- 주민등록번호 (6자리-7자리 패턴)
- 신용카드번호 (4자리-4자리-4자리-4자리 패턴)
- 전화번호 (010-XXXX-XXXX 등)
- 이메일 주소 (xxx@xxx.xxx 패턴)
- 계좌번호 (은행명 + 10~14자리 숫자)
- 여권번호, 운전면허번호

# 출력 형식
아래 JSON 형식으로 정확히 출력하세요. 다른 텍스트는 포함하지 마세요.

{
  "pii_detected": true 또는 false,
  "findings": [
    {
      "type": "검출된 PII 유형",
      "value": "검출된 원본 값",
      "masked": "마스킹 처리된 값",
      "severity": "critical 또는 high",
      "location": "텍스트 내 위치 설명"
    }
  ],
  "action": "pass 또는 fail",
  "reason": "판정 사유"
}
```

---

## 3. 실습: Guardrail 시뮬레이션

### Step 1. 개인정보가 포함된 응답 만들기

초안 프롬프트(v0.1)로 EC-01(개인정보 포함 문의)을 실행합니다.
개인정보 처리 지침이 없는 초안 프롬프트에서는 AI가 고객 정보를 그대로 반복할 가능성이 높습니다.

### Step 2. Guardrail 프롬프트 실행

Step 1에서 생성된 AI 응답을 Guardrail 프롬프트의 `{ai_response}`에 넣고 실행합니다.

### Step 3. Before vs After 비교

| 구분 | Guardrail 미적용 | Guardrail 적용 후 |
|------|-----------------|------------------|
| 카드번호 | 응답에 그대로 노출 | 검출 → Fail 판정 → HITL 리뷰 |
| 이메일 | 응답에 그대로 노출 | 검출 → Fail 판정 → HITL 리뷰 |
| 전화번호 | 응답에 그대로 노출 | 검출 → Fail 판정 → HITL 리뷰 |
| 조치 | 바로 고객에게 발송됨 | Slack 리뷰 후 승인/수정/반려 |

# Part B. Human-in-the-Loop: 슬랙을 통한 결과 리뷰

> **목적**: 판정 트랙에서 Fail이 난 응답에 대해 담당자가 최종 판단합니다.
> HITL은 Fail 시에만 작동하며, Pass된 응답은 자동 발송됩니다.

---

## 1. Fail 판정 조건 (HITL Trigger 발동 기준)

아래 조건 중 하나라도 해당하면 Fail → HITL Trigger가 발동됩니다.

| # | Fail 조건 | 판별 방법 | 이유 |
|---|-----------|----------|------|
| 1 | **PII 검출** | PII Guardrail에서 개인정보 감지 | 보안 리스크 → 사람의 확인 필수 |
| 2 | **환불/결제 문의** | 키워드: 환불, 결제, 카드, 청구, 취소, 구독해지 | 금전 관련 → 회사 정책에 따른 정확한 안내 필요 |
| 3 | **강한 불만/클레임** | 부정 감정 키워드 + 감탄/물음표 3개 이상 | 고객 이탈 리스크 → 숙련된 상담사 판단 필요 |
| 4 | **참조 문서 외 질문** | 응답에 "확인 후 안내" 류 표현 포함 | Hallucination 방지 → 사람이 정확한 정보 확인 |
| 5 | **경쟁사 비교 요청** | 타사 제품/서비스명 포함 | 브랜드 리스크 → 공식 포지셔닝 준수 필요 |

---

## 2. HITL 워크플로우

```
[AI 응답 초안 생성]
       │
       ▼
[PII Guardrail 검사]
       │
       ▼
[판정: Pass / Fail]
       │
   ┌───┴───────┐
   │           │
  Pass        Fail
   │           │
   ▼           ▼
[자동 발송]  [HITL Trigger → Slack 리뷰 요청]
   │                    │
   │              ┌─────┼─────┐
   │              │     │     │
   │            승인   수정   반려
   │              │     │     │
   │              │     ▼     ▼
   │              │  [수정 반영  [프로세스
   │              │   → 재리뷰]   종료]
   │              │
   ▼              ▼
[고객 응답 전달] ◀─┘
```

## 3. Slack 리뷰 메시지 템플릿

Fail 판정 시 담당자(U08QLPUKBFG)에게 Slack DM으로 전송되는 메시지 형식입니다.

```
🔔 AI 응답 리뷰 요청

❌ 반려 → 프로세스 종료 (수동 대응 전환)
```

---

## 4. HITL 액션별 후속 흐름

### ✅ 승인
- AI 응답 초안을 그대로 고객에게 발송합니다.
- Eval Log에 `hitl_action: 승인`, `final_result: 승인 후 발송`으로 기록됩니다.

### ✏️ 수정
- 담당자가 응답을 직접 수정합니다.
- 수정된 응답이 다시 Slack 리뷰 요청으로 올라갑니다.
- 승인 또는 반려가 나올 때까지 이 루프가 반복됩니다.
- Eval Log에 수정 횟수가 기록됩니다.

### ❌ 반려
- 응답을 발송하지 않고 프로세스를 종료합니다.
- 해당 문의는 수동 대응으로 전환됩니다.
- Eval Log에 `hitl_action: 반려`, `final_result: 반려(종료)`로 기록됩니다.

## 5. 실습: HITL 시뮬레이션

### Step 1. 역할 분담
- **AI 운영자 (1~2명)**: 초안 프롬프트로 AI 응답을 생성하고, 판정(Pass/Fail)을 수행
- **리뷰어 (2~3명)**: Fail 건에 대해 Slack 메시지를 받아 승인/수정/반려를 결정
- **관찰자 (나머지)**: 리뷰 과정을 관찰하고 개선 아이디어 도출

### Step 2. 시나리오 실행

| 시나리오 | Test Case | 예상 판정 | HITL 결과 |
|---------|-----------|----------|----------|
| A | GS-01 (기본 기능 질문) | ✅ Pass → 자동 발송 | HITL 미발동 |
| B | EC-02 (화난 고객 + 환불) | ❌ Fail (환불+불만) | 리뷰 → 수정 → 재리뷰 → 승인 |
| C | EC-01 (개인정보 포함) | ❌ Fail (PII 검출) | 리뷰 → 반려 (PII 마스킹 후 재작성 필요) |
| D | EC-06 (복합 시나리오) | ❌ Fail (PII+환불+불만) | 리뷰 → 수정 → 재리뷰 → 승인 or 반려 |

### Step 3. 디브리핑 토론

- 리뷰어들의 판단(승인/수정/반려)이 일치했는가?
- Fail 조건이 너무 넓은가(리뷰 과부하) / 좁은가(위험 응답 누락)?
- "수정 → 재리뷰" 루프는 몇 회 반복이 적정한가?
- Pass 비율이 얼마여야 운영이 현실적인가?

# Part C. 전체 파이프라인 (종합)

## 판정 트랙 + 기록 트랙 통합 흐름

```
[고객 문의 접수]
      │
      ▼
[Customer Agent: 응답 초안 생성]
      │
      ├──────────────────────────┬─────────────────────────┐
      ▼                          ▼                         │
  판정 트랙 (Gate)            기록 트랙 (Record)            │
      │                          │                         │
      ▼                          ▼                         │
  PII Guardrail              Judge LLM 평가                │
      │                          │                         │
      ▼                          ▼                         │
  판정 (Pass/Fail)            Eval Log 기록                │
      │                          │                         │
  ┌───┴────┐                     ▼                         │
 Pass     Fail              평가 리포트                    │
  │        │                                               │
  │        ▼                                               │
  │    HITL Trigger                                        │
  │    (Slack 리뷰)                                        │
  │        │                                               │
  │    ┌───┼───┐                                           │
  │   승인 수정 반려                                        │
  │    │   │    │                                          │
  │    │   ↻   종료                                        │
  │    │                                                   │
  ▼    ▼                                                   │
[고객 응답 전달] ◀─────────────────────────────────────────┘
```

> 💡 **강의 포인트**: 이 파이프라인은 **판정 트랙**과 **기록 트랙**이 병렬로 동작합니다.
> - **판정 트랙**: 보안 위험(PII) + 비즈니스 위험(환불/불만/경쟁사)을 검사하여 발송 여부를 결정
> - **기록 트랙**: 품질 데이터(5차원 채점)를 항상 축적 → 프롬프트 개선의 근거 제공
> - 기록 트랙은 판정에 영향을 주지 않으며, 반려된 응답도 평가 데이터가 기록됩니다.
> - 이 분리를 통해 "발송 판단"과 "품질 측정"의 관심사가 깔끔하게 나뉩니다.
